1. The four join types

JoinWhat it returns
INNER JOINOnly matching rows
LEFT OUTER JOINAll rows from the left table, plus matches from the right
RIGHT OUTER JOINAll rows from the right table, plus matches from the left
FULL OUTER JOINAll rows from both tables

Which table do you want every row from? That decides left vs right. "Left" is the table written before the join keyword, "right" is the one after.

  • All parents, even ones with no children: an outer join on the parent side.
  • Only records that match in both tables: INNER JOIN.
  • Parent listed first, all parents wanted: LEFT OUTER JOIN.
  • Child listed first, all parents wanted: RIGHT OUTER JOIN.

You can play with the join types in the join lab further down.

2. WHERE vs HAVING

QuestionAnswer
Which one filters individual rows?WHERE
Which one filters aggregate results, like Count?HAVING
Which one runs before grouping?WHERE
Which one runs after grouping?HAVING

3. GROUP BY and clause order

  • Every non-aggregate column in SELECT must appear in GROUP BY.
  • GROUP BY is used with aggregate functions. Mix aggregates with plain columns and you must group by the plain columns.
SELECT → FROM → JOIN → WHERE → GROUP BY → HAVING → ORDER BY

4. Common query errors

ErrorWhat's wrong
Aggregate in WHEREAggregates belong in HAVING
Missing GROUP BY columnEvery non-aggregate in SELECT must be in GROUP BY
Ambiguous columnA column that exists in both joined tables must be prefixed with its table name or alias
Wrong join typeUsing INNER JOIN when the question wants all rows from one side (or an outer join on the wrong side)
Clause out of orderWHERE after GROUP BY instead of before

Day 13 and 14

Joins, counts and "never happened"

Parent rows have a primary key. Child rows hold a foreign key pointing back. INNER JOIN keeps only parents that have a child. LEFT OUTER JOIN from the parent keeps every parent and fills the child columns with NULL when there is no match. Two quiz favourites hide in that second case: the count, and the filter for parents with no children.

Join labsample rows, not your real data
OFFICETYPE (parent)
OFFICE (child)

Try FULL OUTER JOIN in the lab: here it matches the left join, because every office must point to an existing office type (a child can't be unmatched). A full join only differs from a left join when both sides can have rows with no partner.

Rules of thumb from your notes: "for all ___" means an outer join from the parent. "Never" means IS NULL (never = NULL) or NOT IN. Count the child's key, not *, when zero is a valid answer. Prefix every column with its table alias whenever there are two or more tables.

Day 14 and 15

Subqueries: the inner query runs first

A subquery is a complete SELECT in brackets, used in WHERE or HAVING. The inner query runs once, and the outer query then runs with its result. Course focus is nested subqueries.

Subquery returnsUseExample
One value= > < >= <= <>WHERE MonthlyRent > (SELECT AVG(MonthlyRent) FROM Office)
A listIN / NOT INWHERE StudentID IN (SELECT StudentID FROM Payment)
A list, other comparisons> ANY, > ALL (also <, >=…)HAVING COUNT(x) >= ALL (SELECT COUNT(x) … GROUP BY …)
A tableFROM ( … ) aliasAlias is required in PostgreSQL
Subquery stepperfrom the Day 15 slides
  • With = the subquery must return exactly one value. Several values give "more than one row returned by a subquery used as an expression". Switch to IN.
  • Don't add DISTINCT inside an IN subquery. Your Day 15 slides say testing shows it is slower.
  • > ANY means greater than at least one value (so greater than the smallest). > ALL means greater than every value (so greater than the largest). ANY and SOME are interchangeable.
  • Correlated subqueries are not assessed in SDEV1201 according to your Day 16 handout. Neither are cross joins.
NOT IN and NULL

If the subquery's list contains a NULL, NOT IN returns no rows at all. Foreign keys that are NOT NULL are safe. Otherwise add WHERE column IS NOT NULL inside the subquery.

Day 15

UNION

Stacks the results of two or more SELECTs into one result. UNION drops duplicate rows. UNION ALL keeps them.

  1. Same number of columns in every query.
  2. Similar datatypes in matching positions (a date and a varchar fail).
  3. ORDER BY goes once, at the very end.
  4. Column names come from the first query.

Query 1: lease types
Query 2: office types

Same idea as the slide: 16 students plus 10 staff is 26 rows, but UNION returns 25 because one name appears in both lists.

Day 14 and 16

Views

A view is a saved SELECT with a name. It behaves like a virtual table but stores no data; the query re-runs each time. Uses: simplify complex queries, hide the table structure, control which columns people can see.

DROP VIEW IF EXISTS VW_OfficeTypeRentSummary;          -- lets the script re-run

CREATE VIEW VW_OfficeTypeRentSummary AS
SELECT OT.OfficeTypeDescription,
       AVG(O.MonthlyRent) AS "AVERAGE MONTHLY RENT"     -- alias becomes the view's column name
FROM OfficeType OT
INNER JOIN Office O ON OT.OfficeTypeCode = O.OfficeTypeCode
GROUP BY OT.OfficeTypeDescription;

SELECT OfficeTypeDescription, "AVERAGE MONTHLY RENT"    -- query it like a table, no join needed
FROM VW_OfficeTypeRentSummary
WHERE "AVERAGE MONTHLY RENT" > 500;
  • Syntax: CREATE [OR REPLACE] VIEW name AS SELECT …; and DROP VIEW [IF EXISTS] name;
  • Alias every calculated column. Quoted aliases must be quoted the same way (and are case sensitive) when you select from the view.
  • Create the view before any query that uses it, or you get relation "x" does not exist.
  • A filter on an aggregate ("TOTAL" > 5) goes in the WHERE of the query on the view, because the aggregate is already a plain column there.

Can you INSERT, UPDATE or DELETE through it?

View is built fromModify through the view?
One table, plain columnsYes, and the table's constraints still apply
Two or more tables (joins)No: cannot insert into view, also update and delete
Has DISTINCT, GROUP BY, HAVING, aggregates or UNIONNo
